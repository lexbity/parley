# TD-04 · Aggregate outputs registry, usage normalization and index migration

Slice evidence for TD-001 FR-3/FR-4/FR-5 and NFR-1/NFR-2. Recorded against
`backend` with the TD-04 edits applied.

## What changed

- `migrations/0900_debt_read_indexes.sql` (reserved band [0900,1000), owned by
  `TD-001/TD-04` in `ci/migrations.py::DEBT_MIGRATIONS`): six additive indexes,
  `match_run_mention(match_run_id, entity_id)` with an `entity_id` index, and a
  single idempotent `json_tree` backfill over existing `match_run` rows.
- `crates/parley-service/src/parties.rs`: party usage count is now one statement
  over two indexed probes (`match_run_recipient` UNION
  `match_run_mention_entity`); the request-path `json_tree` is gone.
- `crates/parley-service/src/inference/matcher.rs`: the single production
  writer of `match_run` inserts normalized mention rows in the same transaction
  using the identical extraction rule as the migration backfill.
- `crates/parley-service/src/materials.rs`: `Workspace::list_outputs` is one
  aggregate statement with two derived tables (approval snapshot, latest
  release), `ORDER BY updated_at DESC, id ASC`, an opaque `(updated_at,id)`
  keyset cursor and a hard 500-row cap enforced both at the route and in the
  method. The `for id in ids` loop and the full-body fetch are deleted.
- Contract: `/outputs` gains `limit` and `cursor`, returns `OutputListing`
  (`items: MaterialSummary[]`, `next_cursor`); `MaterialSummary` has no `body`.
  `generated.ts` regenerated; `listOutputs` fixtures are schema-pinned.
- Frontend: `client.ts` decodes the envelope; `AppShell`/`QueueWorkspace` hold
  summaries; `OutputWorkspace.vue` fetches `GET /materials/{id}` on demand into
  a per-session detail cache for the editor, the versions preview and the
  bound-material actions. This is the surface the spec predicted might exist:
  it rendered list bodies (dirty check, "Open this version", versions preview)
  and is now fixed at that surface rather than by re-widening the list.

## Schema deviations from the draft (verified against migrations)

- The shipped column is `agent_run.lease_deadline`, not `lease_deadline_at`;
  the index uses the real column.
- `match_run.id` is `{job_id}:match` and is not a row in `inference_record`, so
  `match_run_mention.match_run_id` references `match_run(id)` ON DELETE CASCADE.
- `edge_evidence` has a composite PRIMARY KEY whose first column is `edge_id`.
  SQLite already uses the equivalent autoindex, so dropping the explicit
  `edge_evidence_edge` index does **not** produce a SCAN. The index is deployed
  as specified, but the before/after EXPLAIN is honestly recorded as
  SEARCH→SEARCH for that read; the other three show SCAN→SEARCH.

## EXPLAIN QUERY PLAN evidence (captured in `tests/td04_indexes.rs`)

| Read | Before | After |
| --- | --- | --- |
| entity-filtered events | `SCAN event` | `SEARCH event USING COVERING INDEX event_entity_cursor (entity_id=?)` |
| dossier direct links | `SEARCH ... sqlite_autoindex_edge_evidence_1` | unchanged (see deviation) |
| usage count | `SCAN match_run USING INDEX sqlite_autoindex_match_run_1` + `SEARCH match_run_mention USING INDEX match_run_mention_entity` | `SEARCH match_run USING INDEX match_run_recipient (recipient_id=?)` + mention SEARCH |
| outputs list | `SCAN mv` / no ordered material index | `SCAN m USING INDEX material_updated` (ordered index walk), head/dossier probes SEARCH |

The plans are captured by dropping and recreating the 0900 index on one
connection, with a unique plan comment so SQLite cannot replay a cached plan.
