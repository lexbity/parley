# U04 verification record (UCR-001 party and task edits)

## Scope and baseline

- Baseline: U01–U03 as implemented in this working tree. U04 adds the
  `party.rename`, `party.set_focus` and `opportunity.set_task_done` registry
  commands, the typed `application::party_edit` and
  `application::opportunity_task` operations, the `party.edit` and
  `opportunity.task.edit` permissions, and the shared REST adapters. No new
  migration is owned by U04: the commands use the existing `entity`,
  `opportunity`, `event` and ledger tables.
- Fixtures in `contract/fixtures/u04/commands/` are synthetic: no real names,
  session tokens, credentials or subject canaries.

## Implemented interfaces

- `application/party_edit.rs`: one transaction-scoped party edit operation
  shared by the commands and the REST entity PATCH adapter. It guards the
  target kind (parties only), re-checks the expected card revision under
  reservation, rejects blank/oversized names and oversized focus, emits one
  `entity.updated` event and returns a true no-op when the requested state
  already holds (FR-2). Contact policy, claims, graph edges and provenance are
  untouched.
- `application/opportunity_task.rs`: `apply_task` (task toggle) and
  `apply_notes_replace` (canonical notes replace) share the revision
  precondition and event emission. Toggle uses the pure `parley-domain`
  rewrite; stale spans, malformed spans and changed lines are typed errors.
  Desired states that already hold are no-ops.
- `commands/party.rs` and `commands/task.rs`: closed descriptors, schemas,
  samples, audit allowlists and the `party.edit` / `opportunity.task.edit`
  permissions. `opportunity.set_task_done` exposes the `opportunity_task`
  picker; the palette freezes the selected span and notes revision from the
  authoritative task picker.
- `commands/http.rs`: the new write commands run through the same schema gate,
  savepoint, approval-free effect debit and ledger finalization as U01/U03.
- REST adapters: `Workspace::update_entity` (party branch), `update_notes`
  and `toggle_task` now call the typed operations; the REST idempotency
  envelope and published statuses are preserved.

## Recovery boundary

- `u04_party_edit_rest_and_command_share_one_operation` proves REST and
  registry party edits converge on one fact, one revision line and one event
  stream, with the REST 412 `STALE_REVISION` and command 409
  `version_mismatch` mapped from the same typed operation.
- `u04_task_toggle_exact_span_and_second_identical_task` proves the second
  identical task is toggled by its exact span while the first and all
  unaddressed bytes stay untouched, that replay returns the stored result, and
  that a fresh key with an already-holding state is a no-op (zero events, zero
  revision change).
- `u04_rest_note_save_and_command_task_toggle_coordinate` races a full notes
  replace against a scoped task toggle from the same base revision; exactly
  one mutation wins and the other terminal-stale-conflicts, so no update is
  lost.
- `u04_party_edit_preserves_policy_claims_graph_and_xss_text` proves contact
  policy rows, active graph edges and edge history remain byte-identical after
  a rename with an XSS-shaped name stored as text.
- `u04_agent_delegated_party_edit_and_task_done` and
  `u04_agent_task_noop_consumes_zero_executed_write` prove the delegated grant
  check, foreign-target denials, executed-write debit only on changed states
  and zero debit for no-ops.
